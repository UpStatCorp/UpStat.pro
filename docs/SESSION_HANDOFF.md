### 3.2 Синхронизация amoCRM — диагностирована, НЕ исправлена. Самое горячее.

Пользователь подключил amoCRM на проде, синхронизация «висела». Прогнали
логи (только чтение, ничего не меняли) — картина полная:

**Корень:** `full_crm_sync` в `app/services/crm_service.py:2200-2207` вызывает
для ЛЮБОЙ CRM один и тот же набор функций
(`sync_crm_deals/leads/contacts/companies/activities`), но эти функции
написаны только под Bitrix24.

**Механизм поломки:** несовместимые сигнатуры одноимённого метода:
```
crm_service.py:223   AmoCRMService._make_api_request(self, endpoint: str, method: str = "GET", **kwargs)
crm_service.py:1423  Bitrix24Service._make_api_request(self, method: str, params: dict = None)
```
Вызов на `crm_service.py:1846` — `service._make_api_request("crm.deal.list", params)`.
Для Bitrix24 это `method="crm.deal.list", params={...}` (верно). Для amoCRM
словарь `params` попадает в позиционный параметр `method`, дальше httpx
делает `method.upper()` → `AttributeError: 'dict' object has no attribute 'upper'`.

**Проглатывание ошибки:** `except Exception` на `crm_service.py:2219` ловит
это молча, пользователю показывается успешное завершение синхронизации.
Результат на проде: `{'deals': 0, 'leads': 0, 'contacts': 0, 'companies': 0,
'products': 0, 'activities': 0}`.

**Стадия `linking` — 227 обречённых запросов, ~80 секунд впустую.**
`link_recordings_to_entities_async` (`crm_service.py:2228`, докстринг
буквально «запрос к Bitrix API crm.activity.get») для amoCRM делает по
одному запросу на каждую запись:
```
https://upstat.amocrm.ru/api/v4crm.activity.get?ID=leads_note_34219303_359851513
```
Слеш между base_url и endpoint отсутствует (склейка строки без разделителя),
метод `crm.activity.get` у amoCRM не существует, `crm_record_id` там вида
`leads_note_…` а не числовой bitrix-id. Все 227 запросов — 404.

**Выборка самих записей — отдельная неэффективность.** 3 минуты 39 секунд
на 227 записей до всяких ошибок (постраничный обход, не баг, но самая
долгая часть общего ожидания).

**Итог на проде:** записи (227 шт., аудио-ссылки на месте, `sync_status='available'`)

   перенести regex-allowlist из вебхук-ветки. Не блокер запуска (страдает

## 6. Правила работы, установленные в этой сессии

- **Разведка → стоп → правка после одобрения.** На задачи с явным риском
  (изменение схемы, ключей, прод-конфигурации) сначала отдельным ходом
  разведка с ограниченной областью поиска и коротким фактическим ответом,
  без правок. Правки — только после явного «приступай» от пользователя.
- **Прод не трогать без явной отмашки.** Чтение (логи, `SELECT`, `docker
  inspect`) — можно всегда для диагностики. Запись/деплой — только по
  прямому указанию, отдельным сообщением.
- **Каждый вывод подтверждать фактическим прогоном, а не рассуждением.**
  В этой сессии минимум три раза статический анализ давал неверный
  результат, который вскрылся только прогоном на копии прод-базы
  (уникальность индексов bitrix_id — реально оказалась наоборот;
  023 недосчиталась 4 операций, потому что дифф строился только с
  чистой БД). Урок закреплён в `docs/ITOG_ALEMBIC.md`.
- **Миграцию, выравнивающую две разошедшиеся базы, нельзя строить из
  диффа только одной из них.** Нужны оба диффа — иначе операции,
  видимые только с одной стороны, теряются молча.
- **`CARRYOVER.md` — обязательная запись перед переходом к следующей
  задаче.** Если в ходе работы всплыло что-то не относящееся к текущему
  заданию (найденный попутно баг, нерешённый вопрос) — фиксировать сразу,
  не держать в памяти «на потом».
- **Не выдавать недоказанное за подтверждённое.** Когда end-to-end
  проверка требует внешних условий, которых нет (живой OAuth-аккаунт,
  согласие пользователя пройти редирект) — прямо сказать, что не
  проверено, и объяснить чего не хватает, а не имитировать проверку.
- **Коммит-сообщения объясняют ПОЧЕМУ, не ЧТО.** Диффа достаточно для
  «что»; сообщение — единственное место, где остаётся мотивация решения.
- **zsh-ловушки при работе с git по коммитам в цикле:**
  `git show "$c:file"` — `zsh` разворачивает `:а`-модификаторы внутри
  подстановки переменной и портит путь молча; писать `git show "$c":file`.
  `git show ... | while read`  — `git show` внутри цикла может съесть
  stdin цикла; перенаправлять `</dev/null` явно.
- **Прод-специфика этого проекта:** после любого пересоздания backend —
  обязательный `docker compose restart nginx` (закэшированный IP апстрима
  иначе даёт 502 на весь сайт). Подробности — `docs/runbook.md` §2.2.
