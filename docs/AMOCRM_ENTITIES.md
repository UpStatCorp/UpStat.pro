## 1. Что было сломано и почему

`full_crm_sync` вызывала для любой CRM один набор функций
(`sync_crm_deals/leads/contacts/companies/activities` и `linking`),
написанных под REST-методы Bitrix24. Для amoCRM не применима ни одна:
методов с такими именами у неё нет. Стадии падали, `except Exception`
записывал 0, и пользователь видел «Все данные актуальны» — ноль от ошибки
был неотличим от честного «сущностей нет».

Разбор механизма — [CARRYOVER.md](CARRYOVER.md) §11.

## 2. Эндпоинты вместо bitrix-овских

| Bitrix24 | amoCRM | Замечание |
|---|---|---|
| `crm.deal.list` | `GET /api/v4/leads?with=contacts,companies` | «lead» в amo — это сделка, а не лид |
| `crm.lead.list` | прямого аналога нет | ближайшее — `/api/v4/leads/unsorted` (неразобранное) |
| `crm.contact.list` | `GET /api/v4/contacts?with=companies` | |
| `crm.company.list` | `GET /api/v4/companies` | |
| `crm.activity.list` | аналога нет | у amo это `notes` и `tasks` — другая сущность |
| `crm.deal.productrows.get` | `GET /api/v4/catalogs/{id}/elements` | у большинства клиентов каталоги не включены |
| `crm.dealcategory.list` + стадии | `GET /api/v4/leads/pipelines` | воронки со статусами приходят одним ответом |
| `user.get` | `GET /api/v4/users` | |

Пагинация другая: `page`/`limit` и `_links.next` вместо `start`.
Лимит частоты у amoCRM — порядка 7 запросов в секунду; уточнить по
актуальной документации перед этапом 2, где появится инкрементальная
выборка.

## 3. Модель данных: что ложится, что нет

### Ложится без изменения схемы

Идентификаторы у amoCRM целочисленные, поэтому существующая колонка
`bitrix_id` (`Integer`, `UniqueConstraint(integration_id, bitrix_id)`)
подходит физически. Имя врёт, но миграция не нужна — переименование
косметическое, и смешивать его с функциональной правкой не стоит.

`CRMDeal` ← `/leads`:

| Колонка | Поле amoCRM |
|---|---|
| `title` | `name` |
| `opportunity` | `price` |
| `stage_id` | `status_id` |
| `category_id` | `pipeline_id` |
| `stage_name`, `category_name` | из справочника `/leads/pipelines` |
| `close_date` | `closed_at` (unix) |
| `created_at`, `updated_at` | unix-таймстампы |
| `assigned_by_id` | `responsible_user_id` |
| `assigned_by_name` | из справочника `/users` |
| `contact_id`, `company_id` | `_embedded`, основной помечен `is_main` |

`CRMContact` и `CRMCompany` ложатся почти один в один. Телефон и почта —
не атрибуты объекта, а элементы `custom_fields_values` с кодами `PHONE`
и `EMAIL`.

### Правило закрытия сделки — не маппинг поля

У amoCRM **нет** признака «сделка закрыта», в отличие от `CLOSED=Y`
у Bitrix24. Закрытость выражена двумя зарезервированными статусами,
одинаковыми во всех воронках аккаунта:

- `142` — успешно реализовано → `closed=True, is_won=True`
- `143` — закрыто и не реализовано → `closed=True, is_won=False`
- любой другой статус → `closed=False, is_won=None`

Для открытой сделки `is_won` именно `None`, а не `False`: аналитика
считает выигрыши по `is_won == True`, и «ещё не выиграна» не должна
попадать в проигрыши.

Реализация — `_amocrm_outcome` в `app/services/crm_service.py`.

### Не ложится

- `CRMDeal.probability` — у amoCRM нет, поле останется пустым.
- `CRMDeal.source_id`/`source_name`, `loss_reason` — у amo это
  пользовательские поля и отдельный справочник `loss_reason_id`,
  не стандартные атрибуты.
- `CRMLead` — заполнять нечем, если не тянуть «неразобранное».
- `CRMActivity` — прямого аналога нет.
- `CRMDealProduct` — отдельный API каталогов.

## 4. Привязка записей к сущностям

Отдельная реализация, а не адаптация bitrix-ветки — но дешевле, чем
кажется.

`link_recordings_to_entities_async` читает `owner_type`/`owner_id`
с кодами Bitrix24 (`"1"` — лид, `"2"` — сделка), а при их отсутствии идёт
в `crm.activity.get`, которого у amoCRM не существует.

Записи amoCRM из примечаний уже несут нужное: `_get_recordings_from_notes`
кладёт в `crm_metadata` поля `entity_type` (`"leads"`/`"contacts"`)
и `entity_id` — прямой внешний ключ на сущность. Привязка для них —
запрос к БД **без единого обращения к API**.

Разбирать `crm_record_id` вида `leads_note_34219303_359851513` не нужно:
всё уже в метаданных, строка служит только уникальным ключом.

### Записей из `/calls` не бывает — пробела нет

**Исправлено 29.08.2026 по итогам живой проверки.** Раньше здесь было
написано, что записи из `/calls` не привязываются, потому что `contact_id`
не попадает в `crm_metadata`, и что это надо чинить на этапе 2. Это
неверно: **привязывать оттуда нечего**.

`GET /api/v4/calls` отвечает `405 Method Not Allowed` — это эндпоинт для
ДОБАВЛЕНИЯ звонков, читать через него нельзя. Ветка, которая его
опрашивала, ничего не возвращала никогда и ни у кого; общий `except`
превращал 405 в пустой ответ, и в логах это выглядело как «звонков нет».
Ветка удалена, все записи приходят из примечаний.

Следствие: `contact_id` в метаданных `/calls` не нужен, добивать
синхронизированные записи фоновой задачей не нужно, **этап 2 на эту
величину дешевеет**.

### Настоящий пробел — сделки, которых нет в списке

Обнаружен на той же проверке: из 227 записей привязались 103 (все из
примечаний к контактам) и **ни одной** к сделке.

`GET /api/v4/leads` возвращает не все сделки, а только те, у кого назначен
ответственный: на проде 30 из ~128. Записи ссылались на остальные 98,
и их сделок в `crm_deals` просто не было. По прямому `GET /leads/{id}`
такие сделки доступны и отвечают 200.

Закрыто добором: `_amocrm_backfill_deals_from_recordings` собирает
`entity_id` из метаданных записей, отбрасывает уже известные и запрашивает
недостающие поштучно — запрос на сделку, а не на запись, и только пока
их нет в базе. Подробности — [CARRYOVER.md](CARRYOVER.md) §20.

## 5. Что на самом деле ломалось без сущностей

**Не Win Probability.** `calculate_win_probability`
(`app/services/win_probability_service.py`) считает по оценкам чек-листов
разговора; `deal_id`/`lead_id` — необязательные параметры атрибуции.
Пайплайн вызывает её как `calculate_win_probability(conversation_id, db)`
вообще без сделки. Вероятность по каждому разговору у amo-клиента
считалась и раньше.

**Ломался раздел CRM-аналитики:** `revenue`, `avg-check`, `win-rate`,
`conversion`, `cycle` (`app/routers/analytics.py`) — все читают `CRMDeal`.

Нагруженных полей всего шесть:

```
closed, is_won, close_date, opportunity, created_at, assigned_by_name
```

Отсюда приоритет: чтобы закрыть видимую пользователю дыру, достаточно
синхронизировать сделки с этими шестью полями. Лиды, активности и товары
на неё не влияют.

## 6. Этапы

### Этап 1 — день, сделан

- `sync_amocrm_deals` — `/api/v4/leads` с пагинацией и
  `with=contacts,companies`
- `sync_amocrm_contacts`, `sync_amocrm_companies`
- правило `closed`/`is_won` из зарезервированных статусов
- справочники `/leads/pipelines` и `/users` — один запрос на прогон
  вместо запроса на сущность
- `link_amocrm_recordings_to_entities` — по существующим метаданным,
  без обращений к API
- подключение в `_stages_for("amocrm")`

Закрывает CRM-аналитику и привязку записей из примечаний.

### Этап 2 — не начат, стал дешевле

- ~~`contact_id` в метаданные `/calls` и добор уже синхронизированных
  записей~~ — **не требуется**: `/api/v4/calls` не читается (405), записей
  из этого источника не бывает, см. §4
- инкрементальная синхронизация по `filter[updated_at][from]` —
  иначе каждый прогон это полная выборка
- соблюдение лимита частоты запросов

Сделано вне этапа 1, по итогам живой проверки (коммит `7457e47`):
справочники подключены к выборке записей, добор сделок по `entity_id`,
мёртвая ветка `/calls` убрана, статус синхронизации перенесён в Redis
с блокировкой повторного запуска, прогресс обновляется постранично.

### Требует решения, не реализации

- `CRMLead` — тянуть ли «неразобранное» или оставить таблицу пустой
- `CRMActivity` — аналога нет, для amo-привязки не нужна
- `CRMDealProduct` — только если у клиента включены каталоги
- переименование `bitrix_id` → `crm_entity_id` — миграция ради
  читаемости, отдельным заходом
