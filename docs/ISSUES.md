## 1. Пароль от прод-БД в истории git

**Статус:** открыта. Требуется ротация.
**Заведена:** 20.08.2026.

Из `alembic.ini` удалена строка

```ini
sqlalchemy.url = postgresql://saas_user:<пароль>@localhost:5432/saas
```

но **удаление строки из файла не убирает пароль из истории git.** Значение
совпадает с рабочим `POSTGRES_PASSWORD` в `.env`, репозиторий
`UpStatCorp/UpStat.pro` **публичный** — то есть пароль доступен любому, кто
посмотрит историю коммитов.

Строка была нужна только как фолбэк для локального запуска: `alembic/env.py:20`
читает `DATABASE_URL` из окружения и без неё работает.

**Что нужно сделать:**

1. Сменить `POSTGRES_PASSWORD` на проде и в `.env` (пересоздание контейнера
   postgres не требуется — пароль меняется через `ALTER ROLE`).
2. Решить отдельно, чистить ли историю (`git filter-repo` + force-push).
   Ротация обязательна в любом случае, чистка истории — нет: пароль уже
   мог быть проиндексирован.

**Почему не сделано сразу:** ротация прод-пароля — отдельная операция со
своим окном и своими рисками, смешивать её с миграциями было нельзя.

**Связанное:** `.github/workflows/ci.yml` в `detect-secrets` исключает
`alembic/versions`, но не `alembic.ini` — то есть CI в принципе мог поймать
этот пароль. После удаления строки вопрос снят.

## 2. Ключ шифрования CRM-токенов генерируется на импорте модуля

**Статус:** открыта. Следующая задача Tier 0.
**Заведена:** 20.08.2026.

`app/services/crm_service.py:21-48`, функция `_get_persistent_encryption_key()`:
если `CRM_ENCRYPTION_KEY` не задан в окружении, ключ **генерируется на импорте
модуля** и сохраняется в файл `app/.crm_encryption_key`.

Файл лежит в `.gitignore` и **не смонтирован как volume** — то есть в
контейнере он находится в перезаписываемом слое образа. Любое
`docker compose up --force-recreate backend` уничтожило бы его, после чего
модуль сгенерировал бы новый ключ, и токены всех CRM-интеграций стали бы
нерасшифровываемым мусором.

**Фактическое состояние прода на 20.08.2026 (проверено перед деплоем):**

* `CRM_ENCRYPTION_KEY` **задан** в `/home/ubuntu/fastapi/.env` и в окружении
  контейнера, значения совпадают (44 символа, валидный Fernet-ключ);
* файла `/app/app/.crm_encryption_key` в контейнере **нет вовсе** — фолбэк
  ни разу не срабатывал;
* `.env` забэкаплен на сервере в `env_backup_2026-08-20.bak` (права 600).

То есть **прямо сейчас риск не реализован**, и пересоздание контейнеров
(выполненное при деплое 023) прошло безопасно. Опасность в том, что защита
держится только на наличии переменной в `.env`: любая среда, где её забыли
задать, тихо получит одноразовый ключ.

**Что нужно сделать:**

1. Убрать генерацию ключа на импорте — падать с внятной ошибкой, если
   `CRM_ENCRYPTION_KEY` не задан. Молчаливый фолбэк на самосгенерированный
   ключ хуже отказа: он делает данные нечитаемыми не сразу, а при следующем
   пересоздании контейнера.
2. Убрать побочный эффект из импорта модуля: `ENCRYPTION_KEY` и `cipher_suite`
   вычисляются на уровне модуля (строки 47-48), то есть просто импорт
   `crm_service` может создать файл на диске.
3. Проверить `.env.example` — переменная должна быть помечена обязательной.

**Почему не сделано сразу:** правка меняет поведение старта приложения,
её нельзя было смешивать с деплоем миграций в одном окне.
