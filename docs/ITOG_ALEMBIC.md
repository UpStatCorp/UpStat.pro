# Миграции: что было сломано и как теперь

> Итог работы, выполненной 20 августа 2026. Документ для того, кто откроет
> проект через полгода и захочет добавить миграцию.
> Подробности процедур — [runbook.md](runbook.md), разделы 2.2, 3.6–3.8, 4.

---

## Что было сломано

Схему базы данных создавали **не миграции, а `Base.metadata.create_all`**,
который вызывался на старте приложения. Миграции существовали, но их DDL на
проде почти не исполнялся: к моменту их выполнения таблицы и колонки уже
существовали, и guard-условия внутри миграций пропускали блоки целиком —
при этом ревизия штамповалась как применённая.

Проверка это подтвердила жёстко: **ни один индекс, создаваемый только
миграцией и не объявленный в моделях, на проде не существовал.** Всю схему
собрал `create_all`; миграции внесли только данные — сиды параметров (015, 016)
и бэкфилл `product_mode` (020).

Конкретные последствия:

1. **`alembic upgrade head` на чистой базе падал.** Ревизия 001 была пустой
   заглушкой (`def upgrade(): pass`) с докстрингом «Initial schema (created by
   create_all)». Базовой схемы в миграциях не существовало, поэтому 003
   («ALTER TABLE users») падала — таблицы `users` ещё не было. Развернуть
   проект с нуля без `create_all` было невозможно.

2. **Три ядровые таблицы существовали только на проде.** Фича Win Probability
   (коммит `8cbaeeb`, 31.03.2026) выкачена без миграции: `win_probability_scores`,
   `checklist_item_definitions`, `checklist_item_scores` создавал `create_all`.
   На момент правки в них было 1083 строки живых данных.

3. **Проверка версии на старте была сломана трижды.** Ожидаемая ревизия
   захардкожена константой `"018"` при фактическом head `021` — то есть на
   ЗДОРОВОЙ базе каждый из четырёх uvicorn-воркеров писал
   `Alembic version mismatch` на каждом старте, и настоящий рассинхрон в этом
   шуме был неразличим. Широкий `except Exception` глушил отсутствие таблицы
   `alembic_version`. `SELECT ... LIMIT 1` без `ORDER BY` брал произвольную
   строку при нескольких головах.

4. **`create_all` маскировал расхождения, а не чинил их.** Он создаёт только
   отсутствующие таблицы и **никогда не добавляет колонки в существующие.**
   Создав таблицу, он заставлял guard в миграции промолчать — и схема
   расходилась с историей миграций беззвучно.

5. **Второй, мёртвый набор миграций** в `app/alembic/` (001–017). В образ не
   копировался (`Dockerfile` берёт только корневой), разошёлся с рабочим в пяти
   ревизиях. Его 001, в отличие от рабочей, содержала настоящую базовую схему.

6. **`alembic revision` не работал никогда** — в проекте отсутствовал
   `alembic/script.py.mako`. Отсюда и корень всего: все 22 миграции написаны
   руками, поэтому систематически разошлись с моделями (одних только
   расхождений по `nullable` набралось 70).

7. Побочно: в `alembic.ini` лежал реальный прод-пароль в открытом виде.

## Что сделано

| Ревизия / файл | Что |
|---|---|
| `001_initial.py` | Настоящий baseline: 9 таблиц, 71 колонка — те, что миграции 002–021 только ALTER-ят |
| `022_add_win_probability_tables.py` | Три таблицы Win Probability |
| `023_align_schema_with_models.py` | Выравнивание прода и схемы «с нуля» по `app/models.py` |
| `app/db_guard.py` | Проверка схемы; вызывается из `create_app()` и `WorkerSettings.on_startup` |
| `tools/gen_baseline.py` | Генератор baseline из моделей |
| `tools/verify_migrations.sh` | Критерий приёмки одной командой |
| `alembic/script.py.mako` | Шаблон, без которого `alembic revision` не работал |
| CI-джоб `migrations` | Критерий приёмки на настоящем PostgreSQL |

Удалено: `app/alembic/`, `app/alembic.ini`, `Base.metadata.create_all` из
`create_app()`, пароль и мусорный ключ `version_num` из `alembic.ini`.

**Реальных изменений на проде оказалось ровно девять** — остальные ~145
операций ревизии 023 там прошли вхолостую, потому что прод строил `create_all`
из тех же моделей и в этой части был прав:

```
1. crm_recordings.batch_id      varchar(100) -> varchar(20)   (0 строк данных)
2. CREATE INDEX ix_crm_recordings_batch_id
3. CREATE INDEX ix_teams_organization_id
4. CREATE INDEX ix_users_organization_id
5. FK users_premium_granted_by_fkey
6-9. DROP COLUMN users.google_access_token / google_refresh_token /
     google_token_expires_at / is_google_user
```

Четыре удалённые колонки добавила миграция 017, но приложение не читало их
ни разу (проверено грепом по `*.py`, `*.html`, `*.js`, `*.sql`, `*.json` —
находилась только сама 017). Реально использовался дубль `is_oauth_user`
из моделей: `is_google_user` был заполнен у 0 пользователей из 45,
`is_oauth_user` — у 21.

## Что работает теперь

* **С нуля.** `alembic upgrade head` на пустой базе даёт схему, идентичную
  `app/models.py`; последующий `alembic revision --autogenerate` пуст.
* **Прод.** После 022/023 `autogenerate` против копии прод-базы тоже пуст —
  обе схемы сошлись.
* **Обратимость.** `downgrade base` → `upgrade head` проходит целиком.
* **Схему создают только миграции.** `create_all` убран; несоответствие схемы
  роняет старт веба И воркера с явным сообщением, а не пишет warning.
* **Регрессия ловится в CI.** Джоб `migrations` гоняет критерий приёмки на
  настоящем PostgreSQL при каждом PR.

## Правила при добавлении миграций

**1. Не редактировать `001_initial.py` руками.** Он генерируется из моделей:

```bash
python tools/gen_baseline.py            # печатает тело upgrade()
python tools/gen_baseline.py --verify   # сверка с закоммиченным (гоняется в CI)
```

Правило состава: `baseline = app/models.py МИНУС всё, что добавляют 002–021`;
индекс исключается, если исключена хотя бы одна его колонка.

**2. Перед мержем гонять критерий приёмки:**

```bash
DATABASE_URL=postgresql://user:pass@host:5432/ПУСТАЯ_БАЗА bash tools/verify_migrations.sh
```

**3. Идемпотентность — нативным синтаксисом PostgreSQL, а не Python-guard'ами.**
Проект Postgres-only (`app/database.py:9-10` запрещает sqlite):

```python
op.execute("CREATE INDEX IF NOT EXISTS ix_foo ON foo (bar)")
op.execute("ALTER TABLE foo ADD COLUMN IF NOT EXISTS bar INTEGER")
```

Для `SET NOT NULL` guard не нужен вовсе — на уже `NOT NULL` колонке это no-op
без сканирования таблицы.

**4. Идемпотентность писать только там, где расхождение реально существует.**
Каждый guard навсегда остаётся в истории мёртвым кодом. Ревизии 022 и 023 —
исключение с известной причиной, она описана в их докстрингах.

**5. Никогда не вкладывать проверку индекса внутрь проверки колонки.**

```python
# ТАК НЕЛЬЗЯ — ровно это в 018 (строки 79-83, 86-90) стоило проду двух индексов:
if not _column_exists(conn, 'teams', 'organization_id'):
    op.add_column(...)
    if not _index_exists(...):      # <- колонка уже есть -> сюда не зайдём НИКОГДА
        op.create_index(...)
```

**6. Миграцию, выравнивающую две разошедшиеся базы, нельзя выводить из диффа
одной из них.** Ревизия 023 была построена из `autogenerate` на чистой базе
и молча недосчиталась четырёх операций: на чистой базе их уже выполнили 008
и 018, поэтому в дифф они не попали, а на проде их не было. Поймалось только
прогоном на копии прода. **Нужны оба диффа.**

**7. Проверять на копии прод-базы, а не рассуждением.** В ходе работы три
вывода, сделанных статическим анализом, пришлось пересмотреть после
фактического прогона — в том числе про уникальность индексов и про состав
операций 023.

## Границы отката

| Команда | Что делает | Безопасно? |
|---|---|---|
| откат образа | старый код на схеме 023 | **да** — проверено: стартует, `/health` 200, `create_all` схему не меняет |
| `alembic downgrade 022` | вернёт `users.google_*` и `batch_id varchar(100)` | да, данных не теряет |
| `alembic downgrade 021` | дропнет три таблицы Win Probability | **НЕТ — уничтожит живые данные** |

## Как это применялось на проде

20.08.2026, ревизия `021 → 023`, коммит `cc82dad`.

Дельта совпала с предсказанной построчно — ровно девять операций, ни одной
лишней. Данные целы: `users` 45 (из них `is_oauth_user` 21),
`checklist_item_scores` 985, `checklist_item_definitions` 85,
`win_probability_scores` 13, `crm_recordings` 650, таблиц 46,
CRM-интеграции 4 (все активны). Простоя не было: миграции применялись при
работающем старом backend.
