## Открыто на 21.08.2026

### 1. Ни один утёкший секрет не ротирован

**Откуда:** задача «инвентарь секретов», 20.08.2026. Результат —
[SECRETS_ROTATION.md](SECRETS_ROTATION.md) с готовым чеклистом.

**Что не сделано:** чеклист составлен, но не выполнен ни в одном пункте.
Публично доступны с 16.03.2026 (пять месяцев):

- [ ] `OPENAI_API_KEY` — два поколения ключей (135 и 164 символа)
- [ ] `ELEVENLABS_API_KEY`
- [ ] `DEEPGRAM_API_KEY`
- [ ] `AZURE_VOICE_LIVE_API_KEY` / `AZURE_API_KEY`
- [ ] `POSTGRES_PASSWORD` — утёк трижды: `env.example`, исторический `.env`,
      `alembic.ini` (80 из 86 коммитов `main`)
- [ ] `SECRET_KEY` — требует окна, разлогинит всех
- [ ] `ZOOM_CLIENT_SECRET`, `AMOCRM_CLIENT_SECRET` — требуют окна

Пункты 1–4 ротируются **без даунтайма** и не требуют согласований —
это то, что можно было сделать сразу.

### 6. `Lint & Security` красный на `main`

**Откуда:** деплой миграций, 20.08.2026.

Джоб падает на шаге `ruff` минимум с 27.07.2026 — 2514 ошибок,
преимущественно `W293`/`W291` (пробелы в пустых строках). Из-за этого CI
на `main` красный постоянно, и настоящая поломка в нём будет незаметна.
Большая часть чинится `ruff --fix` автоматически.

### 7. `train.upstat.pro` не работает

**Откуда:** постпроверка после деплоя, 20.08.2026.

A-записи в DNS нет, TLS-сертификат покрывает только `upstat.pro`
и `www.upstat.pro`. При этом весь бренд `train` (`BrandMiddleware`,
`TRAIN_HOSTS`, `train_report`, `training_program`) на него завязан,
а `runbook.md` §1.1 предполагает, что домен настроен.

Не связано с деплоем 023: ни nginx, ни сертификаты, ни DNS не менялись.

### 8. Токены всех четырёх CRM-интеграций на проде не расшифровываются

**Откуда:** проверка при правке ключа шифрования CRM, 21.08.2026.

Обнаружено при обязательной проверке «4 интеграции по-прежнему
расшифровываются». Проверено трижды, в том числе **внутри работающего
прод-контейнера его собственным ключом**, сырым `Fernet` в обход кода
приложения:

```
id=13 amocrm   active=True  client_id=FAIL access_token=FAIL refresh_token=FAIL
id=36 bitrix24 active=True  client_id=NULL access_token=FAIL refresh_token=NULL
id=40 amocrm   active=True  client_id=FAIL access_token=FAIL refresh_token=FAIL
id=45 amocrm   active=True  client_id=FAIL access_token=FAIL refresh_token=FAIL
итог: ok=0 fail=10
```

Значения — корректные Fernet-токены (префикс `gAAAAAB`), то есть они были
зашифрованы, но **другим ключом**. Метки времени внутри токенов (Fernet
хранит их в открытом виде): 11.03, 16.03, 28.04 и 19.05.2026. `.env` на
проде последний раз менялся **30.07.2026** — то есть ключ, судя по всему,
сменили уже после того, как интеграции были подключены.

Косвенно согласуется с данными: последняя запись в `crm_recordings` —
19.05.2026, после 30.07 ни одной.

**Это не следствие правки** — до неё поведение было тем же, только ошибка
выглядела как пустой 500 вместо «интеграция требует переподключения».

**Что нужно решить:**
- [ ] найти прежний ключ (бэкапы `.env`, история сервера) — если он есть,
      токены восстанавливаются расшифровкой старым ключом и повторным
      шифрованием текущим, без участия пользователей;
- [ ] если прежнего ключа нет — переподключить четыре интеграции вручную
      через OAuth; данные (650 записей звонков) при этом не теряются,
      теряется только доступ к CRM;
- [ ] решить, помечать ли такие интеграции неактивными автоматически.
      Сейчас все четыре показаны пользователю как активные, хотя не
      работают. В правке от 21.08.2026 статус намеренно не меняется —
      это продуктовое решение.
