### 10. Обновление токенов CRM коммитится в чужую сессию

**Откуда:** там же, 21.08.2026. Подтверждено экспериментом на копии
прод-базы.

`crm_service.py:243`, `:1456`, `:1763` — при 401/expired_token создаётся
**новая** сессия `db = SessionLocal()` и передаётся в
`refresh_access_token(db)` → `save_tokens(db, ...)`. Но `self.integration`
принадлежит другой сессии, поэтому `db.commit()` для этого объекта —
no-op: SQLAlchemy пишет только объекты из identity map своей сессии.

Эксперимент (сессия A владеет объектом, commit в сессии B, A закрыта
без commit): значение в БД **не изменилось**.

Сохранение уцелеет, только если сессия-владелец закоммитится позже сама.
В фоновых задачах синхронизации это не гарантировано.

**Почему это опаснее, чем выглядит:** у amoCRM refresh-токен одноразовый.
Успешный refresh инвалидирует прежний на стороне CRM, а новый в базу может
не попасть — интеграция умирает после первого же обновления токена
и лечится только переподключением вручную.

- [ ] передавать в `refresh_access_token` сессию, которой принадлежит
      `self.integration`, а не создавать новую

### 11. Синхронизация сущностей CRM сломана для amoCRM целиком

**Откуда:** пользователь подключил amoCRM на проде, синхронизация
«висела» ~5 минут. Диагностика по логам прода, 28.08.2026. Только чтение,
правок не делали.

**Корень:** `full_crm_sync` (`crm_service.py:2200-2207`) вызывает для
ЛЮБОЙ CRM один и тот же набор функций
(`sync_crm_deals/leads/contacts/companies/activities`), но эти функции
написаны только под Bitrix24.

**Механизм:** несовместимые сигнатуры одноимённого метода —
`AmoCRMService._make_api_request(self, endpoint: str, method: str = "GET", **kwargs)`
(`crm_service.py:223`) против
`Bitrix24Service._make_api_request(self, method: str, params: dict = None)`
(`crm_service.py:1423`). Вызов на `crm_service.py:1846` —
`service._make_api_request("crm.deal.list", params)` — для Bitrix24 верен,
для amoCRM словарь `params` попадает в позиционный параметр `method`,
дальше httpx делает `method.upper()` →
`AttributeError: 'dict' object has no attribute 'upper'`.

**Проглатывание:** `except Exception` на `crm_service.py:2219` ловит это
молча, пользователю показывается успешное завершение синхронизации.
Факт на проде: `{'deals': 0, 'leads': 0, 'contacts': 0, 'companies': 0,
'products': 0, 'activities': 0}`.

**Стадия `linking` — 227 обречённых запросов, ~80 секунд впустую.**
`link_recordings_to_entities_async` (`crm_service.py:2228`, докстринг
буквально «запрос к Bitrix API crm.activity.get») для amoCRM делает
`https://upstat.amocrm.ru/api/v4crm.activity.get?ID=leads_note_...`.
Все 227 — 404.

**Уточнение 29.08.2026:** механизм здесь ДРУГОЙ, не тот, что у стадий
выше. Вызов в `link_recordings_to_entities_async` идёт с именованным
`params={"ID": ...}`, который у amo уходит в `**kwargs` и дальше в httpx
как query-параметры — `AttributeError` не возникает, `method` остаётся
`"GET"`. Ломается склейка `f"{self.base_url}{endpoint}"` в
`AmoCRMService._make_api_request`: `endpoint="crm.activity.get"` передан
без ведущего слеша, отсюда `…/api/v4crm.activity.get`. Диагноз через
`AttributeError` верен только для `sync_crm_deals/leads/contacts/`
`companies/activities` (позиционный вызов), но не для `linking`.
Плюс метода `crm.activity.get` у amoCRM не существует, а `crm_record_id`
там вида `leads_note_…`, не числовой bitrix-id.

**Выборка записей** — отдельная неэффективность, 3 мин 39 сек на 227
записей, не баг, но основная доля общего ожидания.

**Итог на проде:** записи скачались (227 шт., аудио на месте,
`sync_status='available'`), анализ запускать можно. Сущности CRM не
синхронизировались вообще.

**Исправление 29.08.2026:** раньше здесь было написано, что не работает
Win Probability. Это неверно. `calculate_win_probability`
(`app/services/win_probability_service.py:77`) считает по оценкам
чек-листов разговора, а `deal_id`/`lead_id` — необязательные параметры
атрибуции; пайплайн вызывает её как
`calculate_win_probability(conversation_id, db)` (`pipeline.py:748`)

- [ ] тогда же появится, что показывать в прогрессе

### 19. N+1 в выборке записей — по запросу на каждое примечание

На каждое примечание идёт отдельный справочный запрос за названием сделки
(`_get_lead_name` → `/leads/{id}`) и именем менеджера (`_get_user_name` →
`/users/{id}`). На проде каждый занимает **2–7 секунд**:

```
02:20:39  GET /api/v4/leads/34296679   200
02:20:43  GET /api/v4/leads/34296067   200      +4 с
02:20:50  GET /api/v4/users/12120614   200      +7 с
```

Это и есть «3 минуты 39 секунд на 227 записей», зафиксированные в §11.
При двух параллельных прогонах (§15) время удваивается.

**Важно для оценки объёма:** кэши справочников уже написаны —
`_amocrm_user_names` и `_amocrm_statuses` в `app/services/crm_service.py`,
по одному запросу на прогон. Они сделаны для синхронизации сделок и к
выборке записей просто не подключены. Это не «плюс день» из этапа 2,
а подключение существующего кода.

- [ ] переиспользовать `_amocrm_user_names` в `_get_recordings_from_notes`
- [ ] названия сделок брать из уже синхронизированных `crm_deals`,
      а не запросом на каждое примечание

### 20. `/api/v4/leads` отдаёт не все сделки — привязка к сделкам не работает

Самая весомая находка живой проверки: из 227 записей привязались **103**
(все из примечаний к контактам) и **ни одной** из 124 примечаний к сделкам.

Диапазоны идентификаторов не пересекаются и стыкуются встык:

```
сделки в crm_deals:       31116055 … 33011097   (30 шт.)
сделки в примечаниях:     33018593 … 34632865   (98 шт.)
```

Проверено прямыми запросами к API:

```
/leads?limit=250&page=1  ->  200, получено 30, _links=['self']  (next нет)
/leads?limit=250&page=2  ->  204 No Content
/leads/34296679          ->  200  ← сделка существует и доступна по прямому GET
```

То есть пагинация работает верно — amoCRM честно сообщает, что список
кончился на 30. Список просто отдаёт не все сделки. Разница в полях:

| | есть в списке (`33011097`) | нет в списке (`34296679`) |
|---|---|---|
| `responsible_user_id` | `12120614` | `0` |
| `group_id` | `0` | `-1` |

`/leads` возвращает только сделки с назначенным ответственным — те, что
видит пользователь токена (`current_user_id: 12120614`). Сделки без
ответственного в список не попадают, но по прямому `GET /leads/{id}`
доступны.

**Это недоработка реализации этапа 1, а не поведение amoCRM «как есть»:**
оценка исходила из того, что список отдаёт все сделки, и добор по
идентификаторам из примечаний заложен не был.

Объём починки ограничен: 98 различных `entity_id` — это 98 точечных
запросов **один раз**, а не запрос на каждое примечание.

Побочно: у таких сделок `name` вида «Сделка #34296679» и `price: 0` —
даже после добора выручка по ним будет нулевой. Насколько это отражает
реальность аккаунта, должен сказать владелец.

- [ ] добирать сделки по `entity_id` из метаданных записей, которых нет
      в результате списочной выборки
- [ ] перепроверить после добора, сколько из 124 записей привязалось
