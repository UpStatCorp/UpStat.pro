## 4. `.gitignore`: что покрывает, а что нет

**Ключевой факт: `.gitignore` не действует на уже отслеживаемые файлы.**
Правила для `backup.sql`, `server.log`, `test.db`, `cookies.txt` и `.env`
в файле **есть**, но эти файлы были добавлены в индекс до появления правил —
и правила на них не распространяются.

```bash
git check-ignore -v backup.sql            # ничего — файл отслеживается
git check-ignore --no-index -v backup.sql # .gitignore:25:backup.sql
```

| Файл | Правило в `.gitignore` | Фактически |
|---|---|---|
| `.env`, `.env.rf`, `.env.kz.bak` | есть (`.env`, `.env.*`, `*.bak`) | игнорируются |
| `Voice-Live-Api-main/.env` | есть (`.env`) | **отслеживается**, правило не действует |
| `backup.sql` | есть (`backup.sql`) | **отслеживается** |
| `server.log` | есть (`*.log`) | **отслеживается** |
| `test.db` | есть (`*.db`) | **отслеживается** |
| `cookies.txt` | есть (`cookies.txt`) | **отслеживается** |
| `env.example` | **правила нет** | **отслеживается** |
| `certbot-webroot/` | правила нет | не отслеживается (пуст) |
| `app/.crm_encryption_key` | есть | игнорируется |

### Предлагаемая правка `.gitignore`

Добавить в конец. Правила сами по себе ничего не исправят — они начнут
действовать только после `git rm --cached` (шаг 4 чеклиста).

## 5. Чеклист ротации

Порядок выбран так, чтобы сначала закрыть то, что эксплуатируется мгновенно
и безнаказанно (ключи с оплатой по факту), потом — то, что требует окна.

### Этап 0. Подготовка (до всяких изменений)

- [ ] Снять дамп прод-БД и скопировать **с сервера**:
      `ssh upstat 'cd /home/ubuntu/fastapi && docker compose exec -T postgres pg_dump -U saas_user -d saas -Fc > backup_$(date +%F).dump'`
- [ ] Забэкапить `.env` с прода (уже есть `env_backup_2026-08-20.bak`, права 600)
- [ ] Зафиксировать текущие значения в менеджере паролей — понадобятся для отката
- [ ] Проверить биллинг OpenAI / ElevenLabs / Deepgram / Azure на аномальный
      расход: ключи публично доступны с 16.03.2026, **пять месяцев**

### Этап 1. Ключи с оплатой по факту — без даунтайма, делать первыми

Порядок для каждого: создать новый → положить в `.env` → перезапустить →
убедиться, что работает → **только потом** отозвать старый.

- [ ] **OpenAI.** platform.openai.com → API keys → Create new secret key.
      Отозвать **оба** утёкших ключа (135 и 164 символа — разные поколения).
      Обновить `OPENAI_API_KEY` в `.env` на проде.
- [ ] **ElevenLabs.** elevenlabs.io → Profile → API Key → Regenerate.
      Обновить `ELEVENLABS_API_KEY`.
- [ ] **Deepgram.** console.deepgram.com → API Keys → создать новый, удалить старый.
      Обновить `DEEPGRAM_API_KEY`. Проверить, используется ли он вообще:
      `STT_PROVIDER` по умолчанию `whisper_openai`.
- [ ] **Azure Voice Live.** portal.azure.com → ресурс → Keys and Endpoint.
      У ресурса **две пары ключей**: переключить приложение на Key 2,
      перегенерировать Key 1, потом наоборот. Обновить
      `AZURE_VOICE_LIVE_API_KEY` (и `AZURE_API_KEY` в `Voice-Live-Api-main/.env`,
      если этот подпроект ещё используется).

Применение на проде — одним разом после всех четырёх:

```bash
ssh upstat 'cd /home/ubuntu/fastapi && nano .env'          # обновить значения
ssh upstat 'cd /home/ubuntu/fastapi && docker compose up -d --force-recreate backend worker'
ssh upstat 'cd /home/ubuntu/fastapi && docker compose restart nginx'
```

> Рестарт nginx обязателен после пересоздания backend — иначе закэшированный
> IP апстрима даёт 502 на весь сайт (см. [runbook.md](runbook.md) §2.2).

**Как проверить, что подхватилось:**

```bash
# значение в контейнере совпадает с .env (сравнение по хэшу, без вывода секрета)
ssh upstat 'cd /home/ubuntu/fastapi
A=$(grep "^OPENAI_API_KEY=" .env | cut -d= -f2-)
B=$(docker inspect fastapi-backend-1 --format "{{range .Config.Env}}{{println .}}{{end}}" | grep "^OPENAI_API_KEY=" | cut -d= -f2-)
[ "$A" = "$B" ] && echo "совпадает" || echo "РАЗЛИЧАЮТСЯ"'
```

Функционально: загрузить короткий звонок на анализ и дождаться отчёта —
это задействует и STT, и LLM.

### Этап 2. Пароль PostgreSQL — без даунтайма

Один и тот же пароль утёк трижды: `env.example`, исторический `.env`,
`alembic.ini` (80 коммитов).

- [ ] Сгенерировать новый: `openssl rand -hex 24`
- [ ] Сменить на сервере, **не пересоздавая контейнер**:
      ```bash
      ssh upstat 'cd /home/ubuntu/fastapi && docker compose exec -T postgres \
          psql -U saas_user -d saas -c "ALTER ROLE saas_user WITH PASSWORD '\''<новый>'\''"'
      ```
- [ ] Обновить в `.env`: `POSTGRES_PASSWORD` и `DATABASE_URL` (пароль там продублирован)
- [ ] Пересоздать backend и worker, перезапустить nginx
- [ ] Проверить: `docker compose logs backend --tail=50 | grep db_guard` — должна
      быть строка с `revision: ["023"]`; отсутствие строки или рестарты контейнеров
      означают, что пароль не подхватился

> Существующие соединения в пуле продолжают работать со старым паролем до
> переподключения — поэтому даунтайма нет, но пересоздать контейнеры нужно
> в том же окне, иначе после `pool_recycle` (3600 с) начнутся отказы.

### Этап 3. Требуют окна — делать последними

- [ ] **`SECRET_KEY`.** Ротация **разлогинит всех пользователей**: изменение
      ключа инвалидирует все подписанные сессионные cookie. Планировать на
      ночь. Новый: `openssl rand -hex 32`. Обновить в `.env`, пересоздать
      backend, перезапустить nginx.
- [ ] **`ZOOM_CLIENT_SECRET`.** Regenerate в marketplace.zoom.us немедленно
      инвалидирует старый — окно обязательно. Проверить сначала, используется
      ли Zoom вообще: в `docker-compose.yml` переменные `ZOOM_*` **не
      пробрасываются** в контейнер, то есть интеграция, вероятно, не работает.
      Если так — достаточно отозвать ключ и не заводить новый.
- [ ] **`AMOCRM_CLIENT_SECRET`** (утёк в историческом `.env`). Смена сломает
      уже выданные OAuth-токены: интеграции придётся переподключить вручную.
      На проде 4 активные CRM-интеграции — уточнить, сколько из них amoCRM,
      и согласовать с их владельцами.

## 6. Чистка git-истории — процедура (НЕ ВЫПОЛНЯТЬ без решения)

> **Ротация обязательна в любом случае. Чистка истории — нет.**
> Секреты были публично доступны с 16.03.2026: они могли быть склонированы,
> проиндексированы поисковиками, попасть в кэши GitHub и в датасеты
> сканеров. Чистка истории уменьшает будущую экспозицию, но **не отменяет
> факт компрометации**. Сначала меняем ключи, потом решаем про историю.

### 6.1 Что сделать до

```bash
# 1. Полное зеркало — единственная страховка при неудачной перезаписи
git clone --mirror git@github.com:UpStatCorp/UpStat.pro.git upstat-mirror-$(date +%F).git
tar czf upstat-mirror-$(date +%F).tar.gz upstat-mirror-$(date +%F).git
#    хранить вне рабочей машины

# 2. Зафиксировать текущее состояние ссылок
cd upstat-mirror-$(date +%F).git && git show-ref > ../refs-before.txt

# 3. Убедиться, что нет незамерженных веток, которые потеряются
git branch -a --no-merged main
```

Отдельно: предупредить всех, у кого есть клон, **до** force-push. После
перезаписи их локальные ветки разойдутся с origin по всей истории.

### 6.2 Команды

Рекомендуется `git filter-repo` (официально заменил `filter-branch`,
на порядок быстрее и безопаснее):

```bash
brew install git-filter-repo    # или pip install git-filter-repo

# Работать ОБЯЗАТЕЛЬНО на свежем клоне: filter-repo отказывается
# запускаться в репозитории с настроенным origin и незакоммиченными правками
git clone git@github.com:UpStatCorp/UpStat.pro.git upstat-clean
cd upstat-clean

# Вариант А — вырезать файлы целиком из всей истории
git filter-repo \
    --invert-paths \
    --path env.example \
    --path backup.sql \
    --path server.log \
    --path test.db \
    --path cookies.txt \
    --path .env \
    --path Voice-Live-Api-main/.env

# Вариант Б — заменить значения секретов, сохранив файлы
# (нужен для alembic.ini: файл нужен, а строка с паролем — нет)
cat > /tmp/replacements.txt <<'EOF'
<пароль-БД>==>***REMOVED***
<ключ-openai>==>***REMOVED***
<ключ-elevenlabs>==>***REMOVED***
<ключ-deepgram>==>***REMOVED***
<ключ-azure>==>***REMOVED***
EOF
git filter-repo --replace-text /tmp/replacements.txt

# Проверить, что вычищено
git log --all --oneline -S'<пароль-БД>' | wc -l    # должно быть 0
git ls-files | xargs grep -lE 'sk-[A-Za-z0-9_-]{20,}'   # должно быть пусто

# Вернуть origin (filter-repo его намеренно удаляет) и запушить
git remote add origin git@github.com:UpStatCorp/UpStat.pro.git
git push --force --all origin
git push --force --tags origin
```

Вариант Б предпочтительнее для `alembic.ini`: файл нужен проекту, вырезать
его целиком нельзя, а `--replace-text` заменит только строку с паролем во
всех 80 коммитах.

### 6.3 Риски

| Риск | Пояснение |
|---|---|
| **Меняются ВСЕ хэши коммитов** | `4ecd327` — первый коммит, любая правка в нём переписывает всю историю целиком, 86 коммитов на `main` |
| **Ссылки на коммиты становятся мёртвыми** | Хэши в issue, PR, changelog, в этом и других документах `docs/` перестанут разрешаться. В репозитории на них ссылаются `ITOG_ALEMBIC.md`, `ISSUES.md`, докстринги миграций 020/022/023 |
| **GitHub хранит старые объекты** | Коммиты остаются доступными по прямой ссылке из кэша и из PR ещё какое-то время. Нужен запрос в поддержку GitHub на их удаление |
| **Незамерженные ветки** | `feat/rf-ai-layer-migration` на origin и локальные `security/untrack-secrets`, `claude/blissful-ishizaka-4194f7` придётся перебазировать вручную или потерять |
| **Прод-сервер имеет свой клон** | `/home/ubuntu/fastapi` — рабочий git-клон. После force-push `git pull` там упадёт; понадобится `git fetch origin && git reset --hard origin/main`, а перед этим — проверить, что untracked-файлы (аватары пользователей, дампы) не пострадают |
| **`--force-with-lease` не спасёт** | При перезаписи всей истории проверка «не изменилось ли на сервере» бессмысленна — нужен именно `--force` |

### 6.4 Что сломается у тех, кто уже клонировал

* `git pull` завершится ошибкой «refusing to merge unrelated histories»
  либо создаст дублирующую историю.
* Правильное действие для каждого:
  ```bash
  git fetch origin
  git checkout main
  git reset --hard origin/main      # локальные незапушенные коммиты потеряются
  ```
* Незапушенные ветки нужно перенести **до** перезаписи: сохранить патчами
  (`git format-patch`) и наложить заново поверх новой истории.
* Открытые PR придётся пересоздать: их базовые коммиты исчезнут.

### 6.5 Альтернатива, которую стоит рассмотреть всерьёз

Учитывая, что репозиторий **публичный, форков нет, звёзд нет**, а секреты
доступны пять месяцев, — вместо чистки истории может быть дешевле и честнее:

1. Ротировать все ключи (разделы 5.1–5.3) — **обязательно в любом случае**.
2. **Сделать репозиторий приватным.** Это закрывает будущую экспозицию
   мгновенно и без перезаписи истории.
3. Историю оставить как есть, а факт компрометации задокументировать.

Чистка истории оправдана, если репозиторий должен остаться публичным.
Если публичность не является требованием — пункт 2 решает задачу
надёжнее и без рисков раздела 6.3.
