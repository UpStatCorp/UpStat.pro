1. Контекст и задача

Для части клиентов (в том числе российских команд продаж) нужен упрощённый сценарий: менеджеры каждый день заходят в платформу и проходят голосовые тренировки с ИИ-тренером — без загрузки звонков, без CRM-синхронизации и без аналитики по записям.

Целевой пользовательский сценарий: РОП создаёт команду → приглашает менеджеров → менеджеры видят каталог/программу тренировок → проходят 1–2 сессии в день → РОП видит, кто тренировался и с каким результатом.

Ключевой вопрос для решения

Голосовой движок тренировок в UpStat уже выделен в отдельный модуль (voice_assistant/). Связь с анализом звонков сейчас существует только на уровне создания планов (план рождается из отчёта по звонку) и интерфейса (дашборд заточен под анализ). Поэтому задача — не «писать тренировки с нуля», а отделить продуктовый режим.

3. Что нужно добавить в любом случае

Независимо от выбранного способа, потребуется реализовать:

  1. Источник планов без звонка — каталог тренировок и/или программа на N дней (из существующих промптов в app/static/docs/trainings/).
  2. Режим продукта — флаг «full» vs «training_only» на уровне команды или аккаунта.
  3. Упрощённый дашборд — «тренировка на сегодня», прогресс, streak, история сессий.
  4. Отключение анализа — скрытие UI и блокировка API: /chat, /calls, CRM, аналитика по звонкам.
  5. Отчёт для РОПа — кто прошёл тренировку сегодня, средний score (без паспорта продавца и дельт по звонкам).
СПОСОБ 1

Feature Flag — один продукт, два режима

Самый быстрый и экономичный путь. Одна кодовая база, одно развёртывание.

Суть подхода

Добавляем поле product_mode на уровне команды (или пользователя при регистрации): full — текущий UpStat; training_only — только тренировки. В зависимости от режима показываем другой дашборд, скрываем пункты меню и закрываем API анализа звонков.

Что делаем технически

Backend

  • Миграция БД: teams.product_mode (enum: full / training_only).
  • Сделать report_message_id в плане тренировок необязательным + поле plan_source (analysis / catalog / program).
  • Новый сервис CurriculumService — создаёт план из каталога промптов без GPT-анализа звонка.
  • Middleware require_full_product на роутерах chat, crm, analytics, owner, pipeline.

Frontend

  • При регистрации или по инвайту — выбор/назначение режима (для B2B лучше через инвайт команды).
  • Новый шаблон dashboard_training.html — главная для training_only.
  • Страница /trainings/catalog — карточки по 5 этапам продаж.
  • Условный рендер сайдбара в _layout_dashboard.html.

Что остаётся общим

Auth, teams, voice_assistant, TrainingValidator, Azure Voice Live, admin промптов, notifications.

Плюсы

  • Минимальные сроки и бюджет
  • Один деплой, одна БД, одна команда поддержки
  • Фиксы в голосовом движке сразу для всех клиентов
  • Клиент может перейти на full-режим без миграции данных
  • Используем 80% уже написанного кода

Минусы

  • Кодовая база растёт — нужна дисциплина (guards, тесты)
  • Теоретический риск: баг в guard откроет анализ training-клиенту
  • Брендинг «только тренировки» сложнее отделить визуально
  • Общий домен upstat.pro для обоих продуктов
Кому подходит: нужно быстро запустить пилот с 1–3 российскими клиентами, проверить спрос, не вкладываясь в отдельную инфраструктуру.
СПОСОБ 2

Отдельный фронт — один backend, два интерфейса

Продуктово выглядит как два приложения, технически — один сервер и одна БД.

Суть подхода

Backend остаётся единым (FastAPI + PostgreSQL/SQLite). Создаём отдельный UI-слой для training-only: свой landing, свой дашборд, свой набор шаблонов и отдельный URL (например, train.upstat.pro или upstat.pro/train). Роутинг по домену/пути определяет, какой интерфейс отдавать; API общий, но с теми же feature guards.

Что делаем технически

Всё из Способа 1, плюс:

  • Отдельная папка шаблонов: app/templates/train/ — landing, dashboard, catalog, layout.
  • Middleware по Host header или path prefix — выбор «скина» приложения.
  • Отдельный landing и регистрация только для training (без упоминания звонков).
  • Опционально: отдельный CSS/брендинг (логотип «UpStat Train», другие цвета).
  • DNS: поддомен train.upstat.pro → тот же сервер.

Backend

Идентичен Способу 1 — feature flag + CurriculumService + guards. Дублирования бизнес-логики нет.

Плюсы

  • Чистый продуктовый образ для клиента «только тренировки»
  • Маркетинг и продажи могут вести на отдельный URL
  • Backend и голосовой движок — общие, без дубля кода
  • Можно разный onboarding и pricing на landing
  • Меньше путаницы у менеджеров (не видят «лишние» разделы)

Минусы

  • Два набора HTML-шаблонов — больше UI-работы
  • Изменения в общих компонентах нужно проверять в двух UI
  • +1–2 недели к срокам относительно Способа 1
  • Backend всё ещё общий — полной технической изоляции нет
Кому подходит: когда важен отдельный бренд/URL для российского рынка, но не хочется содержать два сервера и две базы данных.
СПОСОБ 3

Отдельный сервис — микропродукт «UpStat Train»

Максимальная изоляция. Отдельный deploy, API и жизненный цикл продукта.

Суть подхода

Выносим training-only в отдельное приложение: свой репозиторий (или monorepo-пакет), свой FastAPI-сервис, своя БД (или схема), свой деплой. Из основного UpStat копируем/выносим только нужные модули: voice_assistant/, модели Training*, auth, teams. Анализ звонков, CRM, pipeline, seller_passport — не включаются вообще.

Что делаем технически

Архитектура

  • Новый сервис upstat-train/ — slim FastAPI: auth, teams, training_plans, voice_assistant.
  • Общий пакет upstat-core/ (опционально) — shared models, training_stages_service, validator.
  • Отдельная БД — только users, teams, trainings, sessions (без conversations, CRM, passport).
  • Отдельный CI/CD, отдельный мониторинг, отдельные env-переменные Azure.
  • SSO или invite-link между продуктами, если клиент позже захочет full-версию.

Стратегия кода

  • Monorepo + shared library — лучший вариант внутри способа 3: один git, два deploy, общие модули через pip path.
  • Полный форк — проще старт, но через 3–6 месяцев расхождение кода неизбежно.

Плюсы

  • Изменения в анализе звонков никак не ломают Train
  • Можно деплоить в RU-регион отдельно (152-ФЗ, локальный хостинг)
  • Отдельный pricing, SLA, roadmap продукта
  • Минимальная attack surface — нет CRM/webhook/upload pipeline
  • Команда может работать параллельно без конфликтов

Минусы

  • Дорого: 2× инфраструктура, 2× деплой, 2× мониторинг
  • Багфиксы в voice_assistant нужно синхронизировать (или shared lib)
  • Дольший time-to-market
  • Миграция клиента full ↔ train — отдельный проект
  • Риск дублирования, если не выделить shared library сразу
Кому подходит: когда training-only — самостоятельный коммерческий продукт на годы вперёд, с отдельной командой, отдельным юрлицом/рынком и требованиями к изоляции данных (например, только РФ-серверы).

8. Рекомендация команды разработки

Оптимальная стратегия: поэтапно 1 → 2 → (опционально) 3

Этап 1 (сейчас): Способ 1 — Feature Flag. Запускаем пилот за 2–3 недели. Проверяем, платят ли клиенты, проходят ли менеджеры тренировки ежедневно, нужен ли РОПу отчёт. Минимальные инвестиции, максимальная скорость обратной связи.

Этап 2 (при 3+ paying клиентах): Способ 2 — отдельный фронт. Добавляем train.upstat.pro и отдельный landing — без переписывания backend. Продукт выглядит самостоятельно, технически остаём на одном сервере.

Этап 3 (только если бизнес-модель подтверждена): Способ 3 — отдельный сервис. Имеет смысл при отдельном P&L, требованиях RU-хостинга или если Train продаётся как самостоятельный SaaS с другой ценой и командой.

Не рекомендуем сразу идти в Способ 3 или дублировать код в отдельный репозиторий без shared library — голосовой движок активно развивается, форк быстро устареет.
